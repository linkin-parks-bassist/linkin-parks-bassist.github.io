KnowledgetreesThe root cause
Why don't agents do the right thing?

Context poisoning.

Too much, irrelevant or conflicting information in context, and agents quietly go off the rails. It doesn't take much.

A little is enough
Pause here. This is the core diagnosis. The problem is not mainly prompt quality or model intelligence. A transformer reasons from whatever is in its context, and if that includes a little irrelevant or conflicting material, its judgment gets worse. Not dramatically, and not always where the bad material is. That is what makes it dangerous.
KnowledgetreesWhy you don't see it

You won't notice. Not at first.

Agents don't fix the mistake · they build around it
This is the part everyone has lived through without having a name for it. The agent makes an odd choice somewhere unrelated. Later work builds on it, and later fixes work around it instead of removing it. Weeks later you run into a mountain of technical debt with more and more crossed wires, and it keeps getting worse. All of it can trace back to a small amount of irrelevant or conflicting material in context.
KnowledgetreesHow the poison gets in
If it doesn't have what it needs at the outset

It goes looking.

It reads whatever documents are lying around, and those were written for humans: narrative, context, frontmatter, history. And they go stale fast.

For agents, resources are hazards
An under-informed agent does not stop and ask. It forages. Every document it opens is written for a human reader who brings memory, context and judgment about which paragraph is current. The agent brings none of that, so it takes in irrelevant and conflicting material along with what it wanted. Search and RAG make foraging faster. They don't change what is being foraged from. We store information for humans, and our new reader is not human.
KnowledgetreesOur current response

So we add more band-aids.

01 / Prompt

Bigger instructions

Load more rules up front. More context, more to conflict.

02 / Process

Rigid plans

Freeze every decision early because adaptation may lose the original intent.

03 / Oversight

Human babysitting

Continuously redirect, remind, approve and re-explain.

04 / Recovery

Handover summaries

Compress a rich working state into prose and hope nothing essential disappears.

Useful mitigations · incomplete model
These are not bad practices. But none of them stops the foraging, and some add to it: bigger instructions are more context to conflict, and handover summaries are one more human-shaped document lying around. They are compensations for the problem, not a fix for it.
KnowledgetreesThe obvious fix
Our best answer is spec-driven development

A single, complete, unchanging source of truth. It's a fantasy.

Specs change the week they're written. And the old docs are still lying around.

Real projects learn as they go
Spec-driven development is the right instinct: if resources are hazards, give the agent one authoritative source and nothing else. But no real project has a complete spec that never changes. Requirements move, implementation teaches you things, and the spec falls behind. Meanwhile every earlier doc, plan and note is still in the repository, waiting to be found.
KnowledgetreesThe turn
Not a better document · a different substrate

We need a truly AI-native solution.

Built for the reader we actually have.

Knowledge shaped for agents, not humans
A breather. Move off spec-driven development without dwelling on it: the instinct is right, and the tools just weren't built for this reader. Everything so far (poisoning, foraging, stale human-shaped docs, specs that can't stay complete) points the same way. Agents need knowledge in their own form: relevant, current, and there before they go looking. Then: "Well, great news."

A filesystem that doubles as an ontology

The question points at the answer.

Paths carry meaning, so knowledge is indexed by relevance. The agent gets exactly what its question needs, from one fact to a whole specification, and nothing else.

The path is half the query
The folders are there because they carry meaning. "How do I test the installer?" already predicts the route. Exact wording is not required; lexical lookup and semantic branches support discovery. Relevance is built into the address: the agent asks its question and loads only the leaves that answer it, instead of foraging through documents and pulling in everything nearby. Nothing irrelevant gets in to poison the context.

Pre-optimised by the reader it serves

Written by agents, for agents.

Human documentation guesses at what its reader will need, then goes stale. Leaves are written by that reader: an agent records what it actually needed, in the form it needed it.

One representation for every kind of knowledge
This mirrors the earlier "human-shaped information" slide. There, each kind of knowledge lived on its own surface, in its own convention. Here, orientation, instructions, policy, state, decisions and facts are all the same kind of thing: a small, addressable answer. The last row explains a lot of why this works so well. A leaf often holds not just raw information but reasoning that has already been done, so the agent picks up where the last one stopped instead of re-deriving it. Because agents write the leaves, they come out shaped the way agents use them, not the way a human guessed they would.
KnowledgetreesWhy it scales
Structure, not search

Inspired by mathematics.

Depth grows roughly with the logarithm of size, so the tree can keep growing while every lookup stays a handful of choices. And the tree is a Grothendieck construction: a family of answers indexed by paths, assembled into one navigable whole.

Logarithmic depth
depth ≈ log_b n

Ten branches per level reach a million leaves in six choices. Each choice narrows the question, so the path is half the query.

A Grothendieck construction
𝒦 = ∫_{p∈𝒫} 𝒜(p), 𝒜 : 𝒫 → Set

Each path p carries its answers 𝒜(p). The Grothendieck construction assembles that indexed family into one category: every leaf sits over its path, and refining the path carries you between leaves.

The path is half the query
A short detour for the mathematically inclined. "Put files in folders" sounds naive; it isn't. First, scale: a tree with branching factor b holds n leaves at depth about log_b n, so it keeps growing while every lookup stays a few directory choices, and each choice discards most of the tree. Second, structure: the paths form a category, each path carries a family of answers, and the Grothendieck construction glues those fibres into a single total category. An object is a leaf at its path; moving along a refinement of the path moves you between leaves. That is the knowledge tree. Don't linger. The point is that the shape is principled, not ad hoc.
KnowledgetreesWhy it works so well
In context is not the same as ready to reason

Don't cache the answer. Cache where reasoning got to.

01 / Context

Transformers reason from context

Whatever the agent effectively knows right now is whatever is represented in its window.

02 / Transformation

Relevant material still needs work

Source, docs, history, search results and even summaries must be interpreted for scope, relevance, authority and dependencies before the next step can use them.

03 / Repetition

Agents keep paying for it

Each session, and each compaction, repeats the same transformation and then throws the result away.

Relevant is not enough · ready is better
Relevance keeps the poison out. This is the second reason it works so well. For a transformer, knowing something means having it in context, but relevant material still has to be interpreted before the next step can use it, and agents redo that every session. Many leaves hold where earlier reasoning got to, so the agent starts from that point. Nothing here removes reasoning. What it removes is rebuilding reasoning that was already done.
KnowledgetreesPersistent
A semantic cache hierarchy
L1KV cacheComputation already internalized in the current inference pass.
L2ContextThe semantic working state the model can use right now.
L3KTAddressable knowledge, already worked into usable form. Survives sessions and compaction; brought into L2 on demand.
Backing storeSources / worldAuthoritative evidence. Missing or disputed knowledge is rebuilt from here.
An analogy, not an implementation
Present this as an intuition, not a literal claim about computer architecture. KT entries are not cached activations. They are persistent text and structure that the model reads again from scratch each time it loads them. What carries over is the shape: each level is slower and more durable than the one above it, the working set gets pulled upward when needed, and the backing store stays the authority. The level that was missing is L3. Without it, anything that falls out of context, at compaction or the end of a session, goes all the way back to raw sources. This is the first property: persistent.
KnowledgetreesSelf-correcting
L3 talks directly to the backing store

Reconnect cached reasoning to reality.

Leaves carry executable proofs against the sources. Relevant proofs run automatically at every startup.

Green

No detected failure

Usable after checking scope and evidence. Green is not a blanket claim of truth.

Yellow

Needs re-verification

Freshness expired. Check the whole answer against evidence before renewing it.

Brown

All hands on deck

A proof failed or a claim was falsified. All other work stops until consistency is recovered from the sources.

Sources remain evidence · a stale entry is invalidated, never trusted
The second property, self-correcting, and it belongs straight after the hierarchy: persistence is only safe if it can correct itself. In this analogy, L3 is not a cache that drifts away from memory on its own. It checks itself against the backing store. The relevant proofs run automatically when every session starts, so the agent learns about any inconsistency before it relies on anything. A brown result is all hands on deck: the agent reports it prominently, stops all unrelated work, works out why the leaf or proof no longer matches reality, repairs it and re-runs the check. Work resumes only once consistency is back, or when the user explicitly chooses to set that particular failure aside. Don't oversell it: proofs cover only what can be checked mechanically, and green is no guarantee of truth. Knowledgetrees do not remove source reading, testing or judgment.
KnowledgetreesWhy atomisation matters
Not memoization

Retrieve less.
Resume
further ahead.

The agent does not replay a stored trajectory. It retrieves the few leaves relevant to the task, and composes them for the problem in front of it.

$ kt where am i
→ orientation: a README, for agents
$ kt what is next
→ the next action
$ kt how to behave
→ policy: replaces AGENTS.md
$ kt why does cogent_ring_buffer_reindex_generation call shuffle_partition_key_query
→ code-comment-level rationale
$ kt how many dedekind complete ordered fields are there
→ anything else
Small pieces, factored in advance
This is why atomisation matters. A big project summary may contain everything needed, but the model still has to find the relevant part and work out scope, authority and dependencies. Small leaves arrive already split into the pieces this particular task needs, at every scale: "where am I" returns essentially a README for agents, "what is next" the next action, "how to behave" the policy that replaces AGENTS.md, and a "why does" question the rationale you would otherwise hope to find in a code comment. The combination is new each time. What the agent reuses is the pieces.
KnowledgetreesFederated
Leaves compose. So do trees.

Many trees. One lookup.

Every repo owns its own .knowledge. Clone it and the knowledge comes along, without leaking everywhere. The tooling manages access.

./.knowledgeThis repo's own tree. Comes with the clone.Always on, here
~/.knowledgeYour global root: preferences and procedures that follow you.Allowed by you
~/domain/.knowledgeA shared domain tree, pulled in where it's relevant.Granted per project
../api/.knowledgeAnother project's tree. Readable only with approval.Ask first
~/private/.knowledgeYour personal notes. Never appears outside its own tree.Force-private
Plural knowledge · composed on demand · access stays with the user
This is the plurality argument, and it matters. There isn't one knowledge base to curate. Every repository carries its own tree, the way it carries its own code. You can keep a global root for yourself and domain trees for things like a hardware platform, and they all add together in one lookup. The tooling decides what is visible where. A repo's tree is local when you work in it; other roots are asked for, and granted per project, per project and its subdirectories, or everywhere. Private roots never leak into other projects' searches. Clone a repo and you inherit its understanding without it spilling into everything else you work on.

KnowledgetreesAccretive
The tree grows because agents use it

A miss becomes an investigation. Then a fill.

Hit
  1. identify what needs knowing
  2. retrieve the relevant leaf
  3. continue
Miss
  1. identify the gap
  2. inspect sources
  3. reason · investigate
  4. capture in KT
  5. next agent hits

Capture works like a cache fill. Resolve the gap once, at the right scope, before the next agent has to pay for it again.

Growth is ordinary maintenance
The third property: accretive. This is where the tree grows itself. Agents already do expensive investigations when they miss. Capturing the checked result, whether as a new leaf or a rewrite of the leaf that owns it, is part of finishing the work, not a separate documentation sprint. A miss does not prove the knowledge is absent: agents retry lookups before treating something as a gap.
KnowledgetreesAccretive, not append-only
Growth without sediment

Current truth has one owner.

When reality changes, rewrite the governing answer. Git keeps history. The active tree tells the next agent what is true now.

$ kt what is the state
→ direct current answer
$ evidence contradicts it
→ invalidate · repair owner · reconcile dependents
$ future agent asks again
→ hit on the repaired entry
Current state is mutable · history is separate
Accretion is not a pile-up. The tree grows by rewriting answers, not by appending to them, so it never silts up with stale chronology the way a wiki or chat log does. This deals directly with stale specs and changing plans. There is one entry per answer, updated in place. If the same conclusion lived in five documents, the five copies would drift apart. Chronology belongs in Git or an explicit history, not mixed into the current truth.
KnowledgetreesThe new workflow
Three properties · one mechanism

Stop paying for the same reasoning twice.

Persistent

Nothing evaporates

Understanding outlives the session and the compaction. A fresh agent reloads it instead of relying on what is left of the chat.

Accretive

Every miss pays forward

A gap is investigated once, captured at the right scope and inherited by every agent after.

Self-correcting

Reality wins

Proofs run at startup. Stale answers are invalidated and repaired from the evidence, in place.

Source remains evidence · knowledge becomes infrastructure
Recap the three properties as one story. Persistent: what agents learn outlives the context window. Accretive: the tree gets better because agents use it. Self-correcting: it stays tied to reality instead of drifting from it. Take away any one and the others fail: persistence without correction spreads stale beliefs, and correction without accretion leaves nothing worth keeping. This is not a promise that agents never fail. It changes the default environment so expensive conceptual work builds up instead of evaporating.
