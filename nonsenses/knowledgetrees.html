A knowledge system for agents

Knowledgetrees: Information Indexed By Natural Language

Knowledgetrees are a stateful, self-growing, self-healing filesystem for agent knowledge. One canonical, agent-navigable substrate that replaces the split between skills, docs, code comments, project memory, plans, specs, policy and notes.

kt
Works with 4 agent harnesses
$ kt how to release the web app

The path is half the query. Knowledge lives at meaningful filesystem paths, so the question points at the answer. An agent fetches only the leaf it needs, and whatever it learns along the way gets written back for the next agent.

A filesystem that doubles as an ontology.

A knowledgetree is usually a .knowledge/ directory. Its paths are not arbitrary folders: they are questions and concepts, and every branch narrows what the agent is asking.

A knowledgetree

LLMs are language models. Let the question point at the answer.

Need to know how to make a plan? Predict how/to/make/a/plan.md. Need to know why a tree is not an index? Descend why/is/a/knowledge/tree/not/an/index.md.

Leaves hold the answer itself, with checked source evidence, at every scale: from an implementation fact about one function to a full specification.

The context window starts with an index into knowledge, not the knowledge itself.

Because agent context is expensive, fragile and temporary.

Useful knowledge is scattered across giant instruction files, READMEs, skill blobs, chat history, plans and source comments. Agents load too much, miss the right thing, or rediscover what another run already worked out.

01 / Cost

Less prompt bloat

Detailed knowledge can exist in abundance without being injected into every run. The cost is paid only when needed.

02 / Continuity

Survives fresh starts

A new worker, compacted session or different model rebuilds context from persistent current knowledge.

03 / Truth

Current truth wins

Update the canonical state, not a chronology the model has to untangle to find which paragraph is newest.

04 / Compounding

Knowledge compounds

Every reusable discovery saves a future reasoning loop, failed command, search or architectural mistake.

05 / Substrate

One substrate, many uses

Procedures, policy, architecture, plans, specs, environment facts and rationale in one namespace.

06 / Composition

Composable by design

Retrieve the general rule, local refinement, current state and rationale separately, then combine what applies.

How it works.

Agents reach a tree through a local MCP server, and hooks keep the discover-and-capture loop running. Access, federation and search sit around that core.

Sixteen tools, MCP-first.

./install registers a local MCP server with Claude Code, Codex, OpenCode and Copilot CLI. Agents are told to use the tools instead of the kt shell command; the shell stays as the fallback. Every tool delegates to the CLI, so access policy, locking and proofs behave identically.

Output is lean: a leaf comes back as its answer body only, with a one-line notice only when it is yellow or brown. Leaves are read whole and changed by exact-match edit, so an agent can only change what it has read, and a stale edit fails instead of clobbering.

Access

Approve without leaving the harness

When an agent hits a restricted root it calls kt_access_request, and your harness asks you via MCP elicitation: this directory, this directory and below, everywhere, or decline. The model never sees or answers the prompt. Grants can be revoked, are tied to a path, and are dropped when their tree disappears.

A guard against self-granting access to private material, not a sandbox.
Hooks

The loop runs itself

Session start injects kt info: procedure, orientation, dictionary, proof summary. After a tool failure the agent is nudged to check kt for a known fix. At task end, one capture-review asks whether anything reusable was learned. Past ~9,500 bytes, Claude Code's hook context cap means the hook just tells the agent to call kt_info.

Reminders, not verification or a security boundary. They grant no permissions.
Federation

Trees in any directory

A user-wide tree carries host and tooling knowledge. A repo has its own, and frontend/, backend/payments/ or any subfolder can have narrower ones. Directory scope selects relevance before semantic paths narrow the question; the nearest root is consulted first.

kt roots shows the active scopes.
Search

Question prefixes are branch boundaries

kt where is vivado walks where/is/ and returns the exact leaf if it exists, otherwise ranks keywords within that branch. kt grep finds exact text, kt dict lists the vocabulary without loading a tree listing, and kt status lists every yellow and brown leaf with the reason.

Search is lexical, not a semantic model. A miss is not proof of absence.

Concrete facts reconnect themselves to reality.

Agents attach small executable proofs to claims that are immediately, mechanically checkable. The goal is not to turn every sentence into code, just to make simple base-level factoids falsifiable.

A leaf with a proof
The repository has a local orientation leaf.

Proof: (verified at 2026-09-20T09:10:00+10:00)

```bash
test -f .knowledge/where/am/i.md
```

green not necessarily false: no failed proof, no expired freshness. It is the default, whether or not a leaf carries a proof. It does not mean true: check the evidence and scope before relying on it.

yellow freshness expired. Unusable until re-verified: check the claims, then kt renew, which is the agent's attestation that it read the whole leaf.

brown falsified, malformed or proof-failing. Stop relying on it and repair it.

A proof run only ever lowers a status. Raising one takes a manual whole-leaf review, except that a verifiable: true leaf, asserting every claim is covered by its proofs, goes green when they all pass. Facts likely to change get expires_every.

Green means not necessarily false, not true. A passing run says only that the selected checks detected no failure at that time. It does not certify current prose, agreement between leaves, or the adequacy of a predicate. If checked evidence contradicts a leaf, repair it before relying on it.

The documentation gets better because agents use it.

Traditional documentation decays because writing it is a separate activity. In a tree, maintenance is part of the work.

The tree contains answers, not pointers

“The refund policy is in customer-guide.pdf” is weak knowledge. A useful leaf states the policy, links its source, and says when to check it again.

Current state is mutable; history is separate

When policy changes, rewrite its owner. Keep the old version in Git if it matters. Don't make the next agent guess which of two versions governs.

Misses get resolved, not shrugged off

New question, kt first. On a miss, the agent works out whether a leaf exists, reads or rewrites the owner, or adds the answer, or records it as unresolved with a blocker and a next check. Capture happens before the next unrelated tool call.

Growth is ordinary maintenance

“Would a future agent have to rediscover this?” If yes, preserving it is part of finishing the work.

Limits.

Scale

Larger trees are untested

Untested at larger sizes. Retrieval works as long as branches stay meaningfully discriminating.

Search

Lexical, not semantic

Ranking is keyword coverage within a branch. No embeddings, no vector database, and that is deliberate.

Scope

Not task management

It gives knowledge continuity. Work still needs bounded objectives, authority, ownership and acceptance criteria.

Adopt it.

Run the install script. It sets up the hooks and the MCP server, and from then on agents use knowledgetrees automatically.

$ ./install

Idempotent, and it refuses to overwrite differing knowledge without --force. Try ./install --dry-run first if you're nervous. Restart your agent harnesses afterwards.

Common questions.

Is this just RAG with folders?

No. RAG treats documents as the corpus and retrieves chunks. A tree makes the maintained semantic answer the primary artifact, with the path taking part in retrieval. Search remains a fallback.

Does every fact need its own file?

No. The design favors useful semantic boundaries, not maximum file count. Orientation, spec, plan and state leaves are deliberate aggregation points.

Does this mean deleting normal documentation?

No. External governing documents, published manuals and human deliverables stay important. The internal, agent-facing source of reusable knowledge is knowledge first; human presentations can be generated or frozen when needed.

Does it replace task management?

No. It provides knowledge continuity, not scoping, authority or acceptance.

What happens when a proof fails?

Stop trusting the claim. Work out whether the fact is stale, the predicate is broken, or the check couldn't run, then update or mark the knowledge accordingly. A failed implementation check does not automatically rewrite a requirement.

Does stored knowledge grant permission to act?

No. Knowledge is kept separate from execution authority, and secrets don't belong in it.

The proposal in one sentence

Knowledge is discovered as needed and captured as learned.

A knowledgetree is a distributed, stateful knowledge environment in which paths encode meaning, agents discover current answers on demand, procedures and policy compose with project state, mechanically checkable facts can revalidate themselves, and every useful piece of work makes the next one easier.
