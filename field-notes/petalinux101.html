PetaLinux 101.

I built my first embedded Linux image: a KV260-targeted PetaLinux build from my own Vivado hardware export.

Goal

Take a KV260 Vivado design through PetaLinux and successfully generate a Linux image. This first experiment ends at the build output, not a hardware boot. Along the way I want to understand what goes into the build, what comes out, and where the choices behind an embedded Linux system differ from a ready-made distribution.

Method

I’m using an agent for documentation lookup, machine checks and setup, while I do the hands-on PetaLinux work and question its conclusions. Agent findings are not automatically things I have learned. This page keeps that distinction visible.

Installation

The agent found Vivado/Vitis 2025.2 already installed. It first tried their unified installer, then found that PetaLinux has a separate installer. I downloaded the 2025.2 .run. The agent's first attempt stopped on missing Ubuntu build packages; it installed the listed prerequisites, and the second attempt reached the licence screen. Ubuntu 24.04 and absent TFTP drew warnings, not failures.

I reviewed the licences and completed the install in my own terminal. Its text said to “click Accept” in a text-only viewer; q closed the viewer and led to the terminal prompt.

bash ~/Downloads/petalinux-v2025.2-11160223-installer.run \
  --dir ~/AMDDesignTools/2025.2/PetaLinux

The agent verified that sourcing settings.sh sets $PETALINUX and exposes petalinux-create, petalinux-config, petalinux-build and petalinux-package. What I actually learned so far: Ubuntu normally uses dash for /bin/sh. The agent initially overplayed that as a problem; we left the shell alone.

Choosing the target

The target was the KV260 because that is the board on my desk. The agent then checked AMD’s BSP list, found no KV260 PetaLinux 2025.2 BSP listed, and used Vivado MCP to confirm KV260 SOM board definitions exist in Vivado 2025.2. We made a matching hardware export rather than assume an older BSP would work. I sourced settings.sh and created ~/Projects/kv260-linux with petalinux-create project --template zynqMP --name kv260-linux. The same shell and OS warnings appeared, but project creation succeeded. This was only a scaffold: no KV260 hardware description or Linux image yet. I found a Rev A1 marking on the board; AMD’s revision labels differ, but I spotted J21, which its table marks as Rev 2.0-only.

In Vivado I created petalinux_bringup under that project and paired the KV260 SOM with the Vision AI Starter Kit carrier card. The agent checked that both selections were saved in the Vivado project file. I added the Zynq UltraScale+ MPSoC to a block design and ran board-preset automation. Validation failed: the preset enabled two PS-to-PL AXI interfaces with unconnected clocks. The agent found AMD’s PS-only remedy; I disabled the unused interfaces and validation passed. I then exported vivado/design_1_wrapper.xsa; Vivado reported success and the agent confirmed the file exists. I imported it with petalinux-config --get-hw-description, kept the detected UART/SD settings and default DTG machine, and got “Successfully configured project.” No image has been built yet.

The first petalinux-build stopped before compiling: XSCT requires libtinfo.so.5, absent from Ubuntu 24.04’s repositories. My attempt to install libtinfo-dev only found the already-installed ncurses development package. The agent verified Ubuntu’s legacy libtinfo5 package; I installed it, and the retry passed that check. It then stopped because Ubuntu’s AppArmor policy blocks BitBake’s user namespaces. AMD documents a temporary host-wide relaxation; after applying it, the build is running. I still need to restore the policy afterward.

What is the build actually making?

This is the part I came for. I know what it is to use Linux; I want to see where a board-specific Linux system comes from. In particular, I wanted the breakpoints between this fresh, template-based PetaLinux build and the ready-made Ubuntu Server 24.04 image offered for the KV260. The agent initially answered in containers—“kernel,” “root filesystem,” “packages”—without showing me what was inside them. I kept asking until we opened the recipes and named programs.

Inputs and process

Our input is not an Ubuntu image. It is a Vivado hardware export (design_1_wrapper.xsa), a PetaLinux project configuration, and an image recipe. The XSA describes the hardware design; it does not contain Linux. PetaLinux uses it to derive hardware-facing configuration such as the device tree, then invokes Yocto/BitBake. BitBake resolves recipes and dependencies, fetches source, cross-compiles for the target, makes packages, and assembles a root filesystem. Here the requested target is petalinux-image-minimal. “Minimal” is the recipe’s name, not a promise of a kernel plus one lonely process. Yocto’s image-generation model helped make the distinction between a recipe, a package and a finished image clearer.

The current selection includes systemd for init/service management, BusyBox for basic commands, and OpenSSH for remote access. The image also names mtd-utils, nfs-utils, pciutils, u-boot-tools, filesystem-making tools, kernel modules and a boot package group. That is a real userspace, not merely a kernel. The menu does not show GNU coreutils or Bash directly selected, but dependencies can still pull software in; the final manifest matters more than those individual ticks. Nor does producing RPM packages during the build prove that the target has a usable package manager or feed.

Where the boundary sits

I wondered what the XSA contributes when our block design has no PL logic or enabled PS-to-PL AXI master ports. The agent inspected the export: it contains PS initialization and hardware-description files, but no bitstream. Its useful contribution is still substantial: the PS configuration identifies DDR and peripherals such as UART, Ethernet, QSPI and SD. PetaLinux uses that hardware information to generate platform configuration and a device tree; the kernel’s existing drivers can then bind to the described PS devices. The XSA is not a driver, and this design does not call for a “trivial FPGA driver” to match nonexistent PL hardware. Disabling those PS-to-PL ports did not disable every AXI-based connection inside the SoC.

Several names sounded like drivers, which prompted a useful distinction. A kernel driver makes hardware usable through the kernel’s interfaces; pciutils gives userspace tools such as lspci a way to inspect what the kernel found. Likewise, MTD is the kernel’s raw-flash subsystem while mtd-utils contains tools for working with it; NFS has kernel and user-space pieces. A package can contain a command, daemon, library, configuration or kernel module: “package” is a delivery unit, not a software layer. e2fsprogs-mke2fs makes an ext filesystem; it is not the ext driver. u-boot-tools is software for working with U-Boot-related data, not U-Boot itself.

I also asked for the extreme case: could the userspace be nothing but a program I supply as /init? Yes. A tiny initramfs could contain a statically linked init and no shell, SSH, systemd, package manager or cat. The kernel would execute it as PID 1; it would need to remain alive. On this board the earlier boot firmware, bootloader and device tree would still exist. That experiment is a useful way to expose what Linux itself requires versus what a distribution chooses to provide. The kernel’s initramfs documentation describes that hand-off.

Why not a pre-built distribution?

The KV260-capable Ubuntu Server 24.04 image is a completed integration: board support, kernel, device tree, root filesystem, service policy and Ubuntu’s package/update machinery have already been selected and assembled. This PetaLinux project starts further down the stack. Our XSA describes a hardware configuration; PetaLinux derives platform settings from it; Yocto recipes specify which kernel and userspace components to build and put into the image. Those are different inputs at different abstraction layers, not two ways of downloading the same operating system.

The overlap is in upstream software, not distribution identity. Both images can contain Linux, systemd and OpenSSH, but the versions, kernel configuration, device tree, included packages, defaults and maintenance model need not match. In Ubuntu, the board integration and distribution choices arrive as a prebuilt whole. Here we own more of those choices—and therefore more of the work of making them coherent. On the KV260, the boot firmware lives in SOM QSPI and U-Boot hands off to the carrier’s SD card; AMD’s boot overview shows another boundary that a compiled root filesystem alone cannot settle. Whether our template-derived image would boot is a separate experiment, not a condition of this one.

That is why embedded Linux builds exist despite ready-made distributions being available: they let a product choose its hardware description, services, commands and update strategy deliberately, rather than inherit a general-purpose machine’s assumptions. They can be very small or fairly rich. The interesting question is not whether this counts as “real Linux”; it is which part of the familiar Linux experience was chosen, built and wired together, and which part was never included.

The manifest is a useful correction to our predictions: it lists 250 installed packages, including systemd, BusyBox, OpenSSH, bash and iproute2. The rootfs archive contains ls and cat. GNU coreutils, apt, dnf, rpm and opkg do not appear as installed packages. This is the first answer based on the produced filesystem rather than the menu. The agent used the workstation’s authorized sudo prompt to restore the temporary AppArmor setting to its original value.

Unrelated field note: I nicked my thumb while cooking dinner. It bled rather a lot. This has no bearing on PetaLinux.

Result: my first embedded Linux image

The build ran for ages and ended with exactly the message I had half expected: 225 errors, nonzero exit code, failure. Of course it did. Then we looked. Every one of those errors concerned a missing shared-state cache entry; BitBake had fallen back to running the real task. Its log said all 6,388 build tasks succeeded. In images/linux sat the kernel (Image), device tree (system.dtb), FIT image (image.ub), root filesystems and package manifest. The apparent failure was a detour through the cache, not the outcome of the build. I had built my first embedded Linux image. That was the experiment. The end.
